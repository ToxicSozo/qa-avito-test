# Дефекты API

Стенд `https://qa-internship.avito.com`, 24 ноября 2026 года. Проверки API выполнялись через Python 3.12 и pytest с новыми учётными записями и объявлениями.

## API-01. Создание отклоняет нулевые счётчики и принимает отрицательные

**Серьёзность P2 (средняя).** Нельзя создать объявление со статистикой без событий. Отрицательные значения искажают данные о взаимодействии с объявлением.

**Предусловие.** Новый пользователь зарегистрирован через `POST /api/1/register` и получил Bearer-токен через `POST /api/1/autorize`.

**Шаги**

1. Подготовить тело для `POST /api/1/item` со своим `sellerID`, уникальным названием, ценой `9900` и статистикой `{"likes":21,"viewCount":11,"contacts":43}`.
2. Поставить `likes=0` и отправить запрос с Bearer-токеном.
3. Повторить запросы с новым названием и одним изменённым счётчиком для `viewCount=0` и `contacts=0`.
4. Повторить те же варианты со значением `-1`. Если объявление создано, извлечь его UUID из `status` и запросить `GET /api/1/statistic/{id}`.

**Ожидалось.** `0` сохраняется как количество событий, создание возвращает `200`. При `-1` запрос отклоняется с `400`. Нижняя граница `0` основана на смысле счётчиков. В коллекции ограничение явно не задано.

**Фактически.** `0` в любом из трёх полей приводит к `400` с ошибкой обязательного поля. `-1` в любом из полей принимается с кодом `200`. При контрольном чтении статистики объявления, созданного с `likes=-1`, счётчик остался отрицательным. Созданные объявления удалены после проверки.

**Автотесты.** `ITEM-07-*`, `ITEM-08-*`. Соседнее валидное значение `1` проверяется в `STAT-02-v1` и `STAT-02-v2`. [Тест-кейсы](./TESTCASES.md#создание-объявления)

## API-02. Статистика доступна после удаления объявления

**Серьёзность P2 (средняя).** Клиент продолжает получать статистику объекта, который API объявлений уже считает отсутствующим.

**Предусловие.** Новый пользователь авторизован и создал объявление со статистикой `{"likes":21,"viewCount":11,"contacts":43}`.

**Шаги**

1. Прочитать статистику объявления через `GET /api/1/statistic/{id}` и `GET /api/2/statistic/{id}`. Оба запроса возвращают `200` и сохранённые счётчики.
2. Удалить объявление по тому же UUID через `DELETE /api/2/item/{id}`.
3. Запросить `GET /api/1/item/{id}` и убедиться, что объявление отсутствует.
4. Повторить запросы статистики обеих версий.

**Ожидалось.** После удаления оба запроса статистики возвращают `404` как для отсутствующего объявления. Коллекция предусматривает `404` для обеих версий. Ожидание о применении этого статуса после удаления следует из жизненного цикла объявления.

**Фактически.** Удаление вернуло `200`, чтение объявления вернуло `404`. Обе версии статистики вернули `200` и `[{"contacts":43,"likes":21,"viewCount":11}]`. Через пять секунд ответ остался тем же. В отдельном сценарии объявление удалили до первого запроса статистики. Через 30 секунд чтение объявления вернуло `404`, а первый запрос к каждой версии статистики снова вернул `200` и исходные счётчики.

**Автотесты.** `STAT-04-v1`, `STAT-04-v2`. [Тест-кейсы](./TESTCASES.md#статистика)

## API-03. Создание сохраняет отрицательную цену

**Серьёзность P2 (средняя).** Клиент получает отрицательную цену объявления.

**Предусловие.** Пользователь зарегистрирован и авторизован.

**Шаги**

1. Выполнить `POST /api/1/item` с Bearer-токеном, своим `sellerID`, уникальным названием, статистикой `{"likes":21,"viewCount":11,"contacts":43}` и `"price":-1`.
2. Извлечь UUID из `status` и выполнить `GET /api/1/item/{id}` с тем же токеном.

**Ожидалось.** Отрицательная цена отклоняется с `400`. Ожидание основано на смысле поля `price`. Нижняя граница цены в коллекции не задана.

**Фактически.** Создание и чтение вернули `200`. В ответе чтения сохранено `"price":-1`. Контрольное создание с `price=1` прошло и сохранило `1`. При `price=0` сервис вернул `400` с сообщением «поле price обязательно» даже при наличии поля в запросе. Правило для нулевой цены требует уточнения.

**Автотест.** `test_exp_01_create_rejects_negative_price`.

## API-04. Создание принимает название из одних пробелов

**Серьёзность P3 (низкая).** API сохраняет объявление с визуально пустым названием.

**Предусловие.** Пользователь зарегистрирован и авторизован.

**Шаги**

1. Выполнить `POST /api/1/item` с Bearer-токеном, своим `sellerID`, ценой `9900`, статистикой `{"likes":21,"viewCount":11,"contacts":43}` и `"name":"   "`.
2. Извлечь UUID из `status` и выполнить `GET /api/1/item/{id}` с тем же токеном.
3. Повторить создание с пустой строкой в `name` для сравнения.

**Ожидалось.** В обязательном названии должен быть хотя бы один непробельный символ. Создание возвращает `400`. Правило о пробелах в коллекции не описано. Ожидание основано на обязательности названия и на контрольном случае с пустой строкой.

**Фактически.** Создание и чтение вернули `200`. В объявлении сохранились три пробела. Запрос с пустой строкой вернул `400` с сообщением «поле name обязательно».

**Автотест.** `test_exp_02_create_rejects_whitespace_only_name`.

## API-05. HTTP-статус и код ошибки статистики v2 расходятся

**Серьёзность P3 (низкая).** Клиент может по-разному обработать один ответ в зависимости от того, какой код использует. HTTP-статус сообщает, что ресурс отсутствует, а тело описывает ошибку входного параметра.

**Предусловие.** Пользователь зарегистрирован и авторизован.

**Шаги**

1. Отправить `GET /api/2/statistic/not-a-uuid` с Bearer-токеном.
2. Сравнить HTTP-статус с полем `status` в JSON.

**Ожидалось.** HTTP-статус и код в теле описывают одну ошибку. В коллекции для v2 указан `404` среди возможных ответов, поэтому тест проверяет согласованность кодов, не фиксируя конкретный статус.

**Фактически.** HTTP вернул `404`. В JSON указано `"status":"400"`, сообщение «передан некорректный идентификатор объявления».

**Автотест.** `test_exp_03_statistics_v2_error_status_is_consistent`.

## API-06. Удаление отсутствующего объявления возвращает разные коды ошибки

**Серьёзность P3 (низкая).** Клиент, который читает код из тела ответа, может принять отсутствие объявления за внутреннюю ошибку и повторить запрос.

**Предусловие.** Пользователь зарегистрирован и авторизован.

**Шаги**

1. Сгенерировать UUID, для которого объявление не создавалось, и отправить `DELETE /api/2/item/{id}` с Bearer-токеном.
2. Создать собственное объявление и удалить его по UUID из ответа на создание. Убедиться, что удаление вернуло `200`.
3. Повторить удаление того же объявления и сравнить HTTP-статус с полем `status` в JSON. Повторить сравнение и для первого запроса.
4. Для контроля прочитать удалённое объявление через `GET /api/1/item/{id}` и отправить `DELETE /api/2/item/not-a-uuid`.

**Ожидалось.** Удаление отсутствующего объявления возвращает HTTP `404`. Если в теле указан числовой `status`, он соответствует HTTP-статусу. [Postman-коллекция](https://github.com/avito-tech/tech-internship/blob/main/Tech%20Internships/QA/QA-trainee-assignment-autumn-2026/postman_collection.json)

**Фактически.** Удаление по сгенерированному UUID и повторное удаление собственного объявления оба возвращают HTTP `404` и `"status":"500"` в JSON. При чтении удалённого объявления получены HTTP `404` и `"status":"404"`. Удаление с синтаксически неверным UUID вернуло HTTP `400` и `"status":"400"`.

**Автотесты.** `EXP-07-never-created` и `EXP-07-deleted`. [Проверки удаления](./TESTCASES.md#удаление-объявления)

## API-07. При строковой цене API сообщает об отсутствии тела

**Серьёзность P3 (низкая).** Сообщение направляет клиента к проверке тела запроса, хотя исправить нужно тип поля `price`.

**Предусловие.** Пользователь зарегистрирован и авторизован.

**Шаги**

1. Отправить `POST /api/1/item` с токеном, своим `sellerID`, уникальным названием, статистикой `{"likes":21,"viewCount":11,"contacts":43}` и строкой `"abc"` в поле `price`.
2. Для контроля отправить новый JSON с теми же валидными параметрами и пропустить поле `price`.

**Ожидалось.** API возвращает `400`. Сообщение указывает на неверный тип цены. В контрольном запросе сообщение указывает на отсутствие обязательного поля.

**Фактически.** Оба запроса вернули `400`. При строковой цене в поле `status` указано «не передано тело объявления». При пропущенном поле в `result.message` указано «поле price обязательно». Поведение подтверждено на двух самостоятельно зарегистрированных учётных записях.

**Автотест.** `EXP-11`. [Публичный баг-репорт SA1GA1](https://github.com/SA1GA1/QA-trainee-assignment/blob/main/BUGS.md#bug-01-при-нечисловой-цене-api-сообщает-что-тело-объявления-не-передано)

## API-08. Короткий пароль описывается как ошибка JSON

**Серьёзность P3 (низкая).** Клиент получает сообщение об ошибке синтаксиса и не узнаёт, какое значение нужно исправить.

**Шаги**

1. Отправить синтаксически корректный JSON в `POST /api/1/register` с новым уникальным именем и паролем `"short"`.
2. Зарегистрировать другого тестового пользователя с рабочим паролем. Отправить его имя и пароль `"short"` в корректном JSON в `POST /api/1/autorize`.

**Ожидалось.** При отказе из-за длины пароля ответ `400` объясняет ошибку поля. Минимальная длина в коллекции не указана. Если регистрация принимает пароль, созданный пользователь должен иметь возможность войти. Для входа с неверным паролем коллекция также допускает `401`.

**Фактически.** Обе ручки вернули `400` и `{"error":"invalid JSON body"}`. Поведение подтверждено в двух независимых прогонах.

**Автотесты.** `EXP-12-register` и `EXP-12-authorize`. [Публичный баг-репорт MaximNguen](https://github.com/MaximNguen/Avito_QA_2026_Autumm_Internship/blob/master/BUGS.md#bug-07-вводящее-в-заблуждение-сообщение-invalid-json-body-при-ошибках-валидации)

## API-09. При запросе объявления без UUID HTTP-статус расходится с кодом в JSON

**Серьёзность P3 (низкая).** Клиенты могут классифицировать один ответ по-разному в зависимости от того, используют они HTTP-статус или код из JSON.

**Предусловие.** Пользователь зарегистрирован и авторизован.

**Шаги**

1. Отправить `GET /api/1/item/` с Bearer-токеном и без UUID после заключительной косой черты.
2. Сравнить HTTP-статус с числовым полем `code` в JSON.
3. Для контроля отправить `GET /api/1/item` с тем же токеном.

**Ожидалось.** Запрос с пустым UUID возвращает `400` или `404`. Поле `code`, если присутствует, совпадает с HTTP-статусом.

**Фактически.** Запрос с завершающей косой чертой вернул HTTP `404` и JSON `{"code":400,"message":"route /api/1/item/ not found"}`. Контрольный запрос без завершающей косой черты вернул `405`. Поведение подтверждено на двух самостоятельно зарегистрированных учётных записях.

**Автотест.** `EXP-13`. [Публичный баг-репорт GeorgiiPoliakov1](https://github.com/GeorgiiPoliakov1/api-test-automation/blob/main/docs/DEFECTS.md#def-api-14-p3-пустой-id-http-404-против-code-400-в-теле)
