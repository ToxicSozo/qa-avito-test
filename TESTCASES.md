# Задание 2.1. Тест-кейсы API

Сценарии проверяют регистрацию и авторизацию пользователя, создание, чтение и удаление объявлений, а также обе версии статистики. Методы, поля и ожидаемые коды сверены с условием и описаниями запросов в коллекции. [Условие Авито](https://github.com/avito-tech/tech-internship/blob/main/Tech%20Internships/QA/QA-trainee-assignment-autumn-2026/QA-trainee-assignment-autumn-2026.md#задание-21-api), [Postman-коллекция](https://github.com/avito-tech/tech-internship/blob/main/Tech%20Internships/QA/QA-trainee-assignment-autumn-2026/postman_collection.json).

Сценарии разделены по операциям API, файлы перечислены [в README](./README.md#структура-проекта). ID связывают сценарии с автотестами и баг-репортами. Если в строке указано несколько вариантов, каждый запускается как отдельный тест.

## Общие предусловия

- Сценарии API используют тестовый стенд из задания и сами готовят данные со сгенерированными логинами и идентификаторами.
- «Пользователь» означает новую учётную запись, если в строке не указано иначе. Для защищённых запросов токен этого пользователя получен через `POST /api/1/autorize`.
- Для создания объявления берутся `sellerID` пользователя, уникальное непустое название, цена `9900` и статистика `likes=21`, `viewCount=11`, `contacts=43`, если в сценарии не заданы другие значения.
- После сценария его объявления удаляются по сохранённым идентификаторам. При ошибке создания или потере ответа фикстура сверяет список этого тестового продавца. При тайм-ауте очистки повторяет незавершённые запросы в конце сессии. Повторный отказ виден в результате pytest. В условии отсутствует метод удаления пользователей.

## Тест-дизайн

- Классы эквивалентности задают валидные и невалидные данные для регистрации, авторизации и работы с объявлениями.
- Для счётчиков проверяются `-1`, `0` и `1`. Нижняя граница `0` выведена из смысла счётчиков событий. В коллекции числовые границы и ограничения на длину полей не заданы.
- Наличие bearer-токена проверяется для каждой защищённой ручки. Переходы состояния объявления проверяются через создание, чтение и отсутствие ресурса после удаления. [ISTQB CTFL 4.0.1, раздел 4.2](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf#page=39).
- Данные создаются для каждого сценария. Результат изменений проверяется запросом на чтение. Эти подходы описаны в публикации платформенной команды Авито. [QA на уровне платформы: как мы строили систему качества](https://habr.com/ru/companies/avito/articles/1047534/).

В коллекции указан формат массива для статистики v1. Формат ответа v2 уточнён на стенде. В обоих случаях возвращается массив из одного объекта со значениями счётчиков. Для STAT-04 ожидание `404` основано на состоянии ресурса после удаления и контракте обеих версий для отсутствующего объявления.

## Наблюдения на стенде

- Для регистрации, авторизации и создания объявления проверены значения `null`, пустые строки, неверные JSON-типы и синтаксически некорректный JSON. Для создания также проверены пропущенные поля внутри `statistics`.
- На стенде проверены оба регистра UUID, точность больших принятых целых чисел и сохранение названий с символами Unicode.
- Пароли длиной 72 байта, представленные ASCII и многобайтовыми символами UTF-8, приняты при регистрации (`201`) и входе (`200`). Регистрация с паролем длиной 73 байта в обоих вариантах вернула `400`. Это наблюдаемая граница стенда. В коллекции ограничение на длину пароля не задано.
- Список собственного продавца сверялся при 1, 5, 6, 10, 11 и 12 объявлениях с одинаковыми названиями и разными данными. UUID и значения совпадали с созданными записями. После каждого из трёх удалений список содержал только оставшиеся объявления. После очистки он был пуст.
- При регистрации логины с пробелами по краям нормализовались, вход с теми же данными возвращал `200`. Вход также прошёл для логина с составным Unicode, логина в форме адреса электронной почты и пароля с пробелами по краям. Тела `null`, массив, число и пустой объект при регистрации, авторизации и создании объявления вернули `400`.
- После повторного входа в новой HTTP-сессии сохранялась доступность объявления, списка и обеих версий статистики. Название с кавычками, амперсандом, плюсом, слешем и эмодзи совпало при чтении по UUID и в списке. Удаление из новой сессии сделало объявление недоступным в первой сессии.
- Четыре защищённых метода чтения без токена ответили `401` с заголовком `WWW-Authenticate` для схемы `Bearer`. Запрос `GET /api/2/item/{id}` с токеном получил `405` с заголовком `Allow`. [RFC 9110, раздел 15.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5)
- При чтении объявления по UUID и в списке продавца поле `createdAt` содержало два смещения `+0300 +0300`. Python `datetime.fromisoformat` отклонил такую строку. Формат поля в коллекции Postman не задан, поэтому результат записан как наблюдение.
